# v3.3.0 — Bound recipients and verified forwarding

Released 2026-09-24. Windows extensions now expose **33 tools**, with five
callable legacy aliases kept off the list. The five default tools and read-only
CLI remain compatible. Distribution: GitHub source tag and `.tgz`, not npm.

## Changes

- `list_line_recent_chats` lists direct/group names and opaque identities active
  within 14 or 30 Taipei calendar days. It does not read message text or media.
- `check_line_send_target` checks recipient identity without messages or GUI.
  Paired `expectedChatRef` and `expectedOwnSenderRef` bind the selected chat
  and current account; mismatches refuse before message reads or input.
- A unique existing direct chat can now be used when unopened contacts have
  the same name. This path requires an already-open exact titled window and
  independent matching of the latest two distinct text records, visible date,
  minute, direction and empty composer. `prepare_line_send_target` reports
  current readiness without typing or sending. Sending repeats the checks.
  Other chat/name collisions still refuse; globally unique targets retain
  automatic opening without a new mandatory preparation step.
- Original-message forwarding uses `prepare_line_forward`,
  `confirm_line_forward`, `verify_line_forward` and `cancel_line_forward`.
  Source, account and one recipient stay bound to the reviewed operation.
  Persistent dispatch intent prevents automatic retries after an uncertain
  Share action. Cancellation applies only before dispatch and is not recall.
- Exact search can select a uniquely readable matching second result.
  Receipt windows remain bounded across Taipei midnight and require overlap
  with the earlier page when a newer page is truncated.

## Verification and limits

349 Node tests passed. Python: 135 run, 127 passed and eight skipped in the
recorded environment. Fresh stdio startup reports the correct version and
33 tools. The release carries the same runtime code as the live-tested
`3.3.0-local.4` candidate.

Real Windows LINE 26.4.2.3957 checks covered bound direct preparation, wrong
chat/account refusals, and one approved plain-text send through the calling
application. A new own local record matched the complete approved text.
The forwarding candidate was also exercised with a synthetic attachment;
its resulting message was subsequently recalled through guided LINE UI.
The special direct preparation took about 5.6 seconds in one observed run,
not a general performance guarantee.

`RECORDED_LOCAL` and matching local records do **not** establish recipient
delivery or read state. Matching attachment filename/size does not prove byte
identity. The special direct path currently requires two distinct visible
text messages on one date; missing, clipped, nontext or ambiguous context
can refuse. Rich features and UI languages beyond the documented live checks
are not newly certified by this release. No private chat content, identifiers,
screenshots or operation receipts are distributed.
